# Recuperação de senha isolada — MIG 3.8

`apps/backend/app/password_recovery.py` define contratos, não armazenamento nem envio reais. `RecoveryRequestService` devolve sempre a mesma mensagem para conta ativa/inexistente e erro de entrega; gera token de 32 bytes aleatórios (base64url, 43 caracteres), guarda por contrato somente SHA-256 do token e expiração UTC de 30 minutos, e entrega o token puro apenas ao provedor interno do link. Nenhum token puro vai para repositório ou log. O provedor futuro deverá enfileirar/observar falhas sem expor existência da conta; rate limiting de recuperação continua obrigatório.

`PasswordResetService` exige `ResetTokenInput` mascarado e senha nova validada/hasheada por Argon2id. `ResetExecutor` **deve** fazer, sob transação/lock do token e usuário ativos: verificar hash/validade/uso único, chamar `SessionRevoker.revoke_all_for_user`, atualizar o hash da senha, consumir token e registrar `PASSWORD_RESET` sem segredos. Falha do Redis aborta a transação de dados e deixa token reutilizável; token inválido/expirado/consumido não muda nada. A suíte usa apenas um executor/revogador de teste sob lock, não prova semântica PostgreSQL–Redis real.

Não há atomicidade distribuída entre PostgreSQL e Redis. A ordem autorizada por AUTH-003 e já usada na pilha legada revoga sessões antes do commit do banco: falha de revogação não troca senha; falha posterior do banco pode invalidar sessões sem trocar senha (seguro, mas exige novo login). A integração precisa coordenar login concorrente e reset, implementar revogação completa no Redis, escolher ORM/migrations Python antes de escrever no banco existente e testar queda/retry. Até isso ocorrer, nenhum endpoint de recuperação está pronto para produção.
