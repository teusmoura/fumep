# Editor e renderer HERO v1

`HeroBlockEditor` é Client e recebe initialValue, images (projeções disponíveis da Biblioteca), onApply e disabled. Remonte com key de proprietário/bloco/versão ao trocar conteúdo. Dados iniciais inválidos não são substituídos. A UI filtra imagens IMAGE/READY com MIME permitido, retém referência atual fora da seleção como indisponível e bloqueia aplicação até resolver/remover essa referência. Seleção não cria cópia física nem concede autorização.

Imagem nova começa informativa: usa alt padrão disponível como ponto de partida ou exige preenchimento contextual. Apenas marcar explicitamente decoração permite alt vazio. Remover imagem remove também alt. CTA opcional exige label não branco/URL segura; drafts inválidos permanecem para correção. onApply recebe dados Zod válidos, aplicação concorrente é bloqueada e falhas mantêm alterações. Aplicar não publica/salva. Não há fetch, credenciais, endpoints ou persistência própria.

`HeroBlockRenderer` valida o envelope HERO v1 e visibilidade, usando título H2 (H1 pertence à composição da página), descrição literal e CTA na mesma aba. Se imageId estiver presente, exige descriptor `heroResolvedImageSchemaV1` compatível com o UUID: IMAGE/READY/NONE, MIME permitido, dimensões positivas limitadas e src normalizado `/media/...` do portal. Referência ausente/inválida/incompatível retorna null para o bloco. Sem imagem, title/description/CTA continuam válidos. Next/Image usa dimensões intrínsecas e unoptimized, evitando processamento paralelo ao Sharp/Worker e cache do otimizador em Preview futuro. Texto/alt/labels são escapados por React, sem HTML ou vídeo.

O descriptor é metadado de transporte resolvido pelo caller, não JSONB salvo no bloco nem prova de autorização. O consumidor backend futuro deve verificar processamento/deleção atual, acesso do owner e publicação/Preview e fornecer uma URL realmente servida pelo portal. Este loop não cria gateway de mídia/rota fictícia ou exposição pública por UUID. Paths de fixtures nos testes são sintéticos. Referências/MediaUsage e resolução real pertencem à integração do owner/publicação; componentes isolados não significam uma página HERO já navegável.

Os componentes usam tokens/cores herdadas, layout fixo responsivo, imagem sem overlay, largura de leitura limitada, controles nativos/labels, alt e URL com ajuda/aria-invalid, status focável e CTA com focus-visible. `frontendBlockRegistry` compõe HERO v1 completo somente PAGE, mantendo TEXT PAGE/ARTICLE; nenhum import React é inserido no contrato API.

Testes cobrem UI/seleção/alt/decorativo/CTA/retensão/concorrência, SSR/escaping/descriptors/versões/bindings e axe-core semântico em jsdom (sem contraste/layout). QA em navegador local usou fixture descartável: 1280×900 e 390×844, temas LIGHT/DARK, uma/duas colunas, imagem sintética carregada, ausência de overflow da página, tabelas com rolagem local/por teclado, foco visível no CTA/controles, bloqueio de CTA perigoso e alt informativo vazio, decoração explícita e status focado ao aplicar. Controles HERO foram ajustados a 44px e espaçamento após inspeção mobile. Também foi verificada aplicação TEXT por teclado no fixture.

Fixture/rota de pixel sintético foram removidos, servidor encerrado, viewport restaurado e aba fechada antes do commit. Não há página demonstrativa publicada. Essa QA localizada não certifica contraste de todos os temas nem substitui E2E/integração real/avaliação manual completa de acessibilidade. Não existe script E2E no projeto neste estágio.
